# Аудит репозитория `dataist_media`

**Дата:** 2026-08-05
**Объём:** весь репозиторий — `service/` (FastAPI-пайплайн), `bot/` (Telegram-бот на aiogram), инфраструктура (`docker-compose.yml`, `deploy.sh`, Dockerfile'ы), `prd.json`, тесты.
**Состояние тестов на момент аудита:** 186 проходили (165 service + 21 bot); после дописывания недостающих по PRD — **201 проходят** (180 + 21).

---

## 1. Что лежит в репозитории

Система «Dataist arXiv Pipeline»: по ссылке на arXiv-статью автоматически создаётся редакционный обзор на русском (+ перевод на английский), обложка через генерацию изображений, брендированная HTML-страница, публикация в GitHub Pages (домен `dataist.ai`) и анонс в Telegram.

| Часть | Назначение | Объём |
|---|---|---|
| `service/` | FastAPI-бэкенд: парсинг arXiv, LLM-генерация (OpenAI), сборка HTML (Jinja2), публикация (локально + GitHub API), отправка в Telegram | ~3,5 тыс. строк |
| `bot/` | Telegram-бот (aiogram 3): интерактивный флоу — выбор заголовка из 10, правка описания обложки, утверждение картинки, публикация, удаление | ~1,3 тыс. строк |
| `prd.json` | PRD: 3 фичи (F001 ingestion, F002 генерация контента, F003 конфигурация), 27 бизнес-правил, 20 сценариев, 24 тест-кейса | 40 КБ |
| `service/config/` | Промпт-профиль, стиль-профиль, HTML-шаблон — конфигурация отдельно от кода (F003) | 3 файла |
| `service/tests/`, `bot/tests/` | pytest-тесты, разложенные по фичам/сценариям PRD | 201 тест |
| `docker-compose.yml`, `deploy.sh`, Dockerfile'ы | Деплой двух контейнеров на GCE-сервер | — |

Документации для человека (README) в репозитории **не было** — только `prd.json`. В рамках этого аудита добавлена спецификация `SPEC.md`.

## 2. Сильные стороны

- **Чистая слоистая архитектура сервиса**: url_resolver → arxiv_parser → content_generator → visual_generator → html_builder → publisher / github_publisher → telegram_delivery; каждый сервис — отдельный класс с одной ответственностью.
- **Трассируемость к PRD**: почти в каждом файле docstring с Feature/Scenario/BR; тесты названы по сценариям (`test_SC00N_*`, `test_BR0NN_*`). Это редкая и ценная дисциплина.
- **Структурированные ошибки**: иерархия `AppException` с `code/message/stage/retriable` (NFR003–004), общие exception-handler'ы.
- **Graceful degradation** заложена и в основном работает: нет фигур — продолжаем (BR005), упала обложка — продолжаем (BR009), упал EN — RU доставляется (BR010), статус `completed_with_warnings`.
- **Конфигурация как данные** (F003): промпты, стиль, HTML-шаблон — версионируемые JSON/HTML-файлы, кешируются, подменяются без правки кода.
- **Тесты** есть, осмысленные, быстрые (без сети), BDD-докстринги; секреты в git не попадают (`.gitignore` покрывает `.env`, deploy.sh передаёт секреты через окружение).

## 3. Находки

### 3.1. Критичные (безопасность)

**C1. HTTP API полностью без аутентификации, порт открыт наружу.**
Ни один эндпоинт `service/api/v1/endpoints/pipeline/*` не проверяет никаких ключей/токенов. `docker-compose.yml` публикует `8004:8004` на все интерфейсы хоста, CORS настроен `allow_origins=["*"]` + `allow_credentials=True` (`service/core/loader.py:29`). Если файрвол GCE не закрывает 8004, любой в интернете может:
- жечь бюджет OpenAI (`/generate-editorial`, `/generate-cover` — самые дорогие вызовы);
- публиковать произвольный HTML в GitHub-репозиторий и на `dataist.ai` (`/build-and-publish` принимает произвольный `article_body`);
- **удалять опубликованные статьи** — `/delete-article` (`steps.py:73`) принимает `{"folder": ...}` и без всякой проверки удаляет файлы из GitHub-репозитория.
*Рекомендация:* убрать проброс порта наружу (бот ходит по внутренней docker-сети `http://service:8004`; наружу порт не нужен — либо `127.0.0.1:8004:8004`), добавить API-ключ через заголовок и проверку в зависимости FastAPI, ужать CORS.

**C2. Telegram-бот не ограничивает пользователей.**
В `bot/core/config.py` объявлен `ADMIN_CHAT_IDS` и `admin_chat_id_list`, но **нигде не используется**. Любой пользователь Telegram, нашедший бота, может запускать пайплайн (расход OpenAI), публиковать статьи на `dataist.ai` и удалять их (кнопка «🗑 Удалить» доступна всем). *Рекомендация:* middleware/фильтр по `admin_chat_id_list` на все хендлеры.

### 3.2. Высокие (функциональность фактически не работает как задумано)

**H1. Публичная EN-версия статьи не публикуется — ссылки битые.**
В `/build-and-publish` (`steps.py`) в GitHub загружается **только RU** `index.html` (+ обложка и фигуры). EN-страница публикуется только локальным `PublisherService` под `ASSET_PUBLIC_BASE_URL`, который в проде (`deploy.sh`) равен `http://localhost:8004/static`. Итог: `en_html_url`, который бот показывает в финальном сообщении и в переключателе RU/EN, — это localhost-ссылка, недоступная читателю. Нарушены SC013 (переключатель языков), SC019/BR022 (доступная EN-версия), BR010 в публичной части. *Рекомендация:* публиковать EN как `{folder}/en.html` (или `{folder}/en/index.html`) в тот же GitHub-каталог и возвращать соответствующий URL.

**H2. `deploy.sh` не настраивает GitHub-публикацию и деплоит из feature-ветки.**
Скрипт формирует `service/.env` **без** `GITHUB_TOKEN`, `GITHUB_REPO`, `GITHUB_PAGES_URL`. С пустым токеном GitHub-шаг в `/build-and-publish` падает (401 → warning), и бот отдаёт localhost-ссылки даже для RU. Кроме того, деплой идёт из ветки `claude/arxiv-telegram-bot-YaDTV`, а не из основной; `service/example.env` тоже не содержит GitHub-переменных (дрейф между `core/config.py` и примером окружения). *Рекомендация:* добавить GitHub-переменные в deploy.sh и example.env, деплоить из main.

**H3. `en_title`/`en_subtitle` теряются на границе API.**
`/build-and-publish` возвращает `en_title`/`en_subtitle` (`steps.py:676-677`), но `response_model=BuildPublishResponseSchema` их **отфильтровывает** (в схеме таких полей нет). Бот честно читает `result.get("en_title", title)` (`review_widget.py:524`) и всегда получает fallback — английское финальное сообщение выходит с русским заголовком. *Рекомендация:* добавить поля в `BuildPublishResponseSchema` (тогда и хак `locals().get(...)` можно убрать, вынеся переменные наружу try-блока).

**H4. Fallback-генерация обложки «без референса» никогда не срабатывает.**
`VisualGeneratorService.generate_cover_image` в ветке без референса вызывает `images.edit(model=..., prompt=...)` **без параметра `image`** (`visual_generator_service.py:129`) — SDK кидает ошибку до HTTP-запроса, `except` возвращает `None`. Т.е. при недоступном референсном изображении обложки не будет вовсе (сейчас маскируется тем, что референс лежит в публичном GitHub). *Рекомендация:* в fallback-ветке использовать `images.generate`.

**H5. Сервис не стартует без `OPENAI_API_KEY` (и зависимости не запинены).**
`steps.py` создаёт сервисы на уровне модуля; `AsyncOpenAI(api_key="")` в openai 2.x (проверено на 2.53.0, которую ставит незапиненный `requirements.txt`) кидает `OpenAIError: Missing credentials` — приложение падает при старте роутинга. На openai 1.x поведение было мягче. Это же — общий риск: **все зависимости обоих компонентов без версий**. *Рекомендация:* зафиксировать версии (pip-tools/uv, хотя бы `>=,<`), клиент OpenAI создавать лениво.

**H6. Дублирование дорогих LLM-вызовов.**
- В `/process` (`PipelineOrchestratorService.run`): `generate_editorial` внутри уже генерирует title, subtitle и links, после чего оркестратор вызывает `generate_title`, `generate_subtitle`, `extract_links` **повторно** — ×2 стоимость и латентность этого пути.
- В `/generate-editorial` (интерактивный флоу): `generate_editorial` генерирует заголовок и подзаголовок LLM-ом, которые эндпоинт сразу перетирает выбранным пользователем `chosen_title` — 2 лишних LLM-вызова на каждую статью.
*Рекомендация:* параметризовать `generate_editorial` (генерировать только то, что нужно вызывающему).

### 3.3. Средние

**M1. HTML-инъекция в собираемых страницах.** Тело статьи вставляется в шаблон через `{{ article_html | safe }}`, а строится f-строками без экранирования (`html_builder_service.py:_process_block`): текст LLM, подписи `[CAPTION:...]`, подписи фигур из arXiv HTML попадают в страницу как есть. Автоэкранирование Jinja работает только для title/subtitle/og. Источники полудоверенные (LLM + arXiv), но с учётом C1 (эндпоинт открыт) любой может опубликовать страницу с произвольным `<script>` на домене dataist.ai. *Рекомендация:* `html.escape()` для текстовых узлов и подписей перед сборкой.

**M2. Мёртвый/битый код в `bot/node/review/`.** `ReviewProcessingAnswer` и `ReviewSuccessAnswer` ссылаются на несуществующие `vocab.MSG_PROCESSING` и `vocab.MSG_SUCCESS` — вызов уронит бота (`AttributeError`). Реальный флоу живёт в `review_widget.py` и использует из этого слоя только `ReviewTrigger`; `ReviewCode` дергает старый `/process`-путь. Это остатки прежней архитектуры «trigger/code/answer». *Рекомендация:* удалить мёртвые классы либо восстановить недостающие константы.

**M3. Зависимости объявлены неаккуратно.** `python-slugify` используется ботом (`review_widget.py`), но в `bot/requirements.txt` его нет — он доустанавливается только в Dockerfile (`RUN pip install ... python-slugify`); локальный запуск без Docker упадёт. В `service/requirements.txt` лежит неиспользуемый `python-telegram-bot` (Telegram зовётся через httpx) и тестовые пакеты (`pytest`, `respx`, `pytest-httpx`) в прод-зависимостях. *Рекомендация:* привести requirements в порядок, тестовые — в отдельный файл.

**M4. Состояние только в памяти.** FSM-состояния aiogram (MemoryStorage по умолчанию) и `_final_cache` (`review_widget.py:40`) теряются при рестарте контейнера: переключатель RU/EN и кнопка «Удалить» под старыми сообщениями перестают работать (для удаления папка хранится в callback_data, поэтому частично переживает). `_final_cache` ничем не ограничен по размеру. *Рекомендация:* по мере роста — RedisStorage; минимум — задокументировать поведение.

**M5. Публикация в GitHub: гонки и ложный успех.**
- `_find_available_folder` → загрузка файлов — классический TOCTOU: два одновременных `build-and-publish` могут выбрать одну папку и перезаписать друг друга.
- `delete_folder` возвращает `True`, даже если **все** DELETE-запросы упали (исключения проглатываются в цикле) — бот покажет «✅ удалена», хотя файлы остались.
- ветка `main` захардкожена в `_put_file`/`delete_folder`.
*Рекомендация:* возвращать `False`/список ошибок при неудачных DELETE; ветку — в конфиг.

**M6. SSRF-векторы в сервисе.** `/generate-cover` скачивает `previous_cover_url` (замена базы на localhost происходит только если URL начинается с `ASSET_PUBLIC_BASE_URL`, иначе URL запрашивается как есть), `/build-and-publish` скачивает произвольные `figures[].url`. В связке с C1 это внутренний HTTP-клиент по указке извне. *Рекомендация:* allowlist доменов (arxiv.org, собственный static).

**M7. Шаблон игнорирует вычисленный `og.image`.** `html_builder_service.build_html_page` заботливо строит `og_image` c fallback на HTTPS-картинку, но шаблон использует `{{ cover_image_url | ... }}` напрямую — логика фолбэка мертва; при localhost-обложке OG-превью в соцсетях будет битым (актуально для локального пути публикации). Плюс захардкоженный fallback-URL картинки повторяется в двух местах (код + шаблон).

**M8. Несогласованность правил URL между ботом и сервисом.** Бот принимает `/pdf/`-ссылки (`review_trigger.py`, `_ARXIV_RE` включает `pdf`), сервис их отвергает (PRD T002: pdf — невалидно) — пользователь с pdf-ссылкой получает не дружелюбное «неверная ссылка», а сырой текст HTTP-ошибки. Старые arXiv ID (`cs/0112017`) не поддерживаются нигде (осознанное ограничение — стоит зафиксировать в доке).

### 3.4. Низкие

- `@app.on_event("startup")` — deprecated в FastAPI (переходить на lifespan); `version: "3.8"` в docker-compose устарел.
- `steps.py` — монолит на 680 строк: три ответственности в одном эндпоинте (`build-and-publish`: локальная публикация + GitHub + Telegram), `import httpx as _httpx` внутри функции при httpx в топе файла, `except (PublishError, Exception)` в оркестраторе.
- В оркестраторе `ru_text` объявляется только внутри `try` шага 9 и читается в шаге 10 — при исключении в `_format_telegram_message` будет `NameError` (практически недостижимо, но паттерн хрупкий).
- Pydantic-схемы `EditorialArticleSchema`, `CoverAssetSchema`, `PublishedPageSchema`, `TelegramMessageSchema`, `HtmlPageArtifactSchema` объявлены, но пайплайн внутри гоняет голые dict'ы — типизация декоративная. Пустые пакеты `service/model/`, `service/repository/`.
- Сервисы создают OpenAI-клиенты в конструкторе — DI отсутствует, тесты вынуждены обходить `__init__` через `__new__`.
- Шаблон тянет внешние CDN (`cdn.tailwindcss.com`, `unpkg.com/lucide@latest` — незапиненная версия, supply-chain риск), `user-scalable=no` вредит доступности; teaser в боте пере-разбивается на абзацы по предложениям, ломая 3-абзацную структуру, которую специально просит промпт.
- PRD внутренне противоречив: SC011 «текст → становится заголовком напрямую» vs BR014 «текст → 10 новых вариантов». Реализация следует BR014 (+ отдельная кнопка «Ввести своё» для прямого ввода) — противоречие стоит починить в PRD.
- Нет CI (тесты не запускаются автоматически), нет README, нет линтера/форматтера в репозитории.

## 5. Тесты

**Было:** 186 тестов, все зелёные, без сети, хорошо привязаны к сценариям. Непокрытые тест-кейсы из `prd.json`: **BR021** (удаление папки из GitHub), сценарий **SC007** на стороне сервиса (RU доставляется при падении EN), **BR025** (редакторский пост-процессинг).

**Добавлено в этом аудите (15 тестов, все зелёные):**
- `service/tests/F004_github_publishing/test_BR021_delete.py` — delete_folder: DELETE для каждого файла (sha+branch в payload), `True`; 404 → `False`; без токена → `False`; записи без sha пропускаются.
- `service/tests/F002_content_generation/test_SC007_en_fallback.py` — оркестратор при падении перевода: RU-URL присутствует, EN отсутствует, warning и failed-step записаны, статус `completed_with_warnings`; RU-only прогон перевод не трогает.
- `service/tests/F002_content_generation/test_BR025_postprocess.py` — пост-процессинг: вызывает LLM с телом статьи в промпте, промпт профиля содержит ключевые замены, при отсутствии промпта возвращает текст без изменений, при падении пост-процессинга `generate_editorial` сохраняет сырой текст.

**Итог: 201 тест, все проходят** (`pytest service/tests` → 180, `BOT_TOKEN` не нужен — bot/tests/conftest.py сам подставляет фиктивный → `pytest bot/tests` → 21).

**Остаются непокрытыми** (кандидаты на следующую итерацию): HTTP-слой `steps.py` (эндпоинты через httpx-мок/TestClient — в частности, регресс на H3), хендлеры `review_widget.py` (сейчас тестируются только callback'и, trigger и состояния), `ArxivParserService.fetch_html` (respx), `TelegramDeliveryService.send_message`, мёртвый код M2.

## 6. Приоритетные рекомендации

1. **Закрыть API** (C1): не публиковать порт наружу + API-ключ; ограничить бот по `ADMIN_CHAT_IDS` (C2). Это один день работы и главный риск прямо сейчас.
2. **Дочинить EN-публикацию** (H1 + H3): публиковать `en.html` в ту же GitHub-папку, добавить `en_title` в схему ответа.
3. **Синхронизировать деплой с кодом** (H2): GitHub-переменные в deploy.sh/example.env, деплой из основной ветки.
4. Починить fallback обложки (H4), лениво создавать OpenAI-клиент и запинить зависимости (H5), убрать двойные LLM-вызовы (H6).
5. Экранировать HTML (M1), удалить мёртвый код (M2), прибрать requirements (M3).
6. Завести CI (GitHub Actions: pytest обоих пакетов), README, линтер.
